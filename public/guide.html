The 10 concepts, mapped to the lab

The lab implements five of the ten concepts directly, in code you can run and test. The other five are design disciplines the lab gestures at — this page is honest about which is which.

Honest limits up front. The "model" is a deterministic rule-based reasoner, not an LLM. Token counts are character/4 estimates. The guardrail policy is illustrative. The lab proves the engineering, not model intelligence.

Start here

What this demo proves

Every run of the loop produces the same engineering guarantees a production agent needs: the loop always terminates (goal, step budget, or the no-progress detector), a flaky tool is recovered by harness retries the model never sees, the context window is compacted when it exceeds budget, and disallowed or over-limit writes are blocked in code — never merely discouraged in prose. The tests assert all four.

Concepts the lab runs for real

Concept 01

Harness engineering

lookup_order is rate-limited on its first call in a run; the harness retries (bounded, transient errors only) and the loop recovers without the reasoner knowing.

See it
Amber Retry events in step 1 of the three scenarios that call lookup_order.
Concept 02

Loop engineering

Three exits are coded into the engine: goal met, step budget (8), and a no-progress detector that kills a loop after the same action repeats with identical args.

See it
?scenario=ghost-order — killed at step 3 of 8.
Concept 03

Context engineering

Every observation is appended to the context with an estimated token cost. Exceed the budget and the oldest observations collapse into a summary line.

See it
The context meter + Context compact events in the refund scenarios.
Concept 07

Guardrails & permissions

Three rules enforced before a tool runs: the task allowlist, a permanent deny on delete_records, and a human-approval gate on refunds above the limit.

See it
?scenario=delete-everything (blocked) and ?scenario=refund-over-limit (gated).
Concept 10

Observability & tracing

Every phase of every step lands in a structured trace with tool, args, verdict, and context size — the same record the tests grade.

See it

Concepts the lab can't prove alone

Concept 04

Tool design

Partially real: tools carry strict schemas and corrective errors ('order_id' must match /^O-\d+$/ (e.g. 'O-778')). What's missing is a real model benefitting from them.

Concept 05

Memory architecture

Each run starts from a fresh world — there is no persistence layer. Memory deserves its own lab.

Concept 06

Orchestration patterns

Deliberately single-agent — the article's advice is to earn multi-agent, not start there.

Concept 08

Evals for agents

The test suite is the eval: it grades trajectories (guardrail fired, retry happened, loop terminated), not just final answers.

Concept 09

Human-in-the-loop

The refund gate models the handoff (over-limit → "routed to a human approver") but no human UI sits behind it — the lab ends at the escalation.

Run locally

Inspect the evidence

npm test        # loop, guardrails, tools, scenario sync, server
npm run scan    # side-by-side scenario report
npm run check   # both
npm start       # serve the lab on :3000

Nothing reaches a network, a model, or a real system — the loop runs entirely in-process.

Limits

What this demo does not claim

  • The reasoner is rule-based and deterministic — it demonstrates the engineering around a model, not model behavior.
  • Token counts are length/4 estimates, not a real tokenizer.
  • The guardrail policy is illustrative, not a complete permissions model.
  • The human-approval gate stops at escalation — there is no approver UI.
  • No memory, no orchestration — single agent, single run.
